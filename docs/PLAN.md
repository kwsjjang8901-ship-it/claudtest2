## 2. 검증 계획

### V1. 측정 조건 확보 (최우선)

| 항목 | 내용 |
|---|---|
| 미러 위치 | DC 트래픽이 보이는 링크 (2차 pcap 구간, eth5 고트래픽 링크 후보). 가능하면 사용자 L2 구간 1곳 추가 |
| 방향 | 양방향 (리포트 "양방향 TCP 비율" 70% 이상 확인) |
| 시간 | 출근 시간대(08:30~09:30) 포함 2시간 이상, 가능하면 업무일 하루 |
| 캡처 방식 | 패킷 개수(`-c`)가 아니라 시간 기준 분할: `tcpdump -i eth5 -s 0 -G 600 -W 12 -w 'eth5_%Y%m%d_%H%M%S.pcap'` |
| 확인 기준 | 리포트 "캡처 시간별 식별률"이 시간에 따라 오르는지, Kerberos·CLDAP 신호 건수 |

### V2. 정답 데이터 수집

캡처와 같은 시간대 기준으로 수집한다. 개인정보가 섞이지 않도록 필요한 컬럼만 받는다.

| 정답 소스 | 받을 컬럼 | 수집 방법 예 | 검증 대상 |
|---|---|---|---|
| AD 컴퓨터 목록 | Name, DNSHostName, IPv4Address, OperatingSystem, OperatingSystemVersion, LastLogonDate | `Get-ADComputer -Filter * -Properties ...` | 머신 계정·호스트명·OS |
| DHCP 임대 목록 | IP, MAC, HostName, LeaseStart/Expiry | `Get-DhcpServerv4Lease` | IP-단말 바인딩, IP 재사용 |
| 스위치 ARP/MAC 테이블 (표본 구간) | IP, MAC, 포트/VLAN | `show ip arp`, `show mac address-table` | conn MAC이 실제 단말 MAC인지, 공유 MAC 판정 |
| 수동 표본 확인 | 자산 30개 무작위 | 담당자 확인 | 서버 역할·OS 판정 |

### V3. 평가 도구 (`tools/evaluate.py`, 신규)

정답 CSV와 `assets.json`을 IP·시간 기준으로 맞춰 아래 지표를 장비 종류별(도메인 PC / 비도메인 PC / 서버 / 기타)로 계산한다.

| 지표 | 정의 |
|---|---|
| 관측률 | 정답 장비 중 캡처 시간에 IP가 관측된 비율 |
| 식별률 | 관측된 장비 중 IP+시간이 아닌 키로 식별된 비율 |
| 정확도 | 식별된 자산 중 호스트명·머신 계정·MAC이 정답과 일치하는 비율 |
| 오결합률 | 정답상 다른 장비 2대 이상이 한 자산에 묶인 비율 |
| 중복률 | 정답상 1대가 자산 여러 개로 나뉜 비율 |
| OS·역할 정확도 | OS 계열/버전, 서버 역할의 일치율 |

### V4. 성능·운영 검증

| 항목 | 방법 | 기준(초안) |
|---|---|---|
| 처리 성능 | 같은 pcap을 AssetID 로드/미로드로 실행해 처리 시간·메모리 비교 | 추가 부하 5% 이하 |
| 패킷 손실 | 실시간 실행 시 `capture_loss.log`, `stats.log` | 손실 0% (기존 nsm_rules 기준과 동일) |
| 메모리 | 24시간 실행 중 중복 억제 테이블(`recent`) 크기 추이 | 상한 내 안정 |
| **Zeek 클러스터** | 워커 2개 이상으로 실행해 단일 프로세스 결과와 비교 | 아래 리스크 참고 |

클러스터 리스크: 중복 억제 테이블과 DHCP 트랜잭션(xid) 테이블이 워커별로 따로 있다.
- 같은 신호가 워커 수만큼 중복 기록될 수 있다(로그량 증가, 판정에는 영향 없음).
- DHCP 요청과 ACK가 서로 다른 워커로 가면 client-id·호스트명이 IP와 이어지지 않을 수 있다.
  Zeek 기본 DHCP 스크립트처럼 클러스터 집계 방식이 필요한지 V4에서 확인한다.

- 운영 pcap에서 발견한 문제는 합성 pcap으로 재현해 테스트로 남긴다(지금까지 mDNS 충돌, CLDAP, 프록시, 비대칭 경로)
